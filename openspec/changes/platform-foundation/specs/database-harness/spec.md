# Database Harness Specification

## Purpose

A reproducible PostgreSQL path: forward-only migrations, a Docker-free real-PostgreSQL test database usable locally and in CI with isolated lifecycle, and the runtime connection through Hyperdrive. Real PostgreSQL is required because later changes test row locking and concurrency.

Source: proposal "Capabilities", Scope #9-10, Approach 4.4-4.5; decisions OD-1 and OD-4 (orchestrator, on recommended defaults).

## Requirements

### Requirement: Forward-only migrations

Schema changes MUST be SQL migrations in `drizzle/`, generated by Drizzle Kit, applied in order and never edited after being applied. Migrations MUST NOT be reverted by down-scripts. A baseline migration MUST exist and MUST create no business tables. (Source: proposal Scope #9, ADR-005)

#### Scenario: Apply from scratch

- GIVEN an empty PostgreSQL database
- WHEN all migrations are applied
- THEN the command succeeds
- AND the latest applied migration id equals the last file in `drizzle/`

#### Scenario: Re-apply is a no-op

- GIVEN a database with all migrations applied
- WHEN the migration command runs again
- THEN it succeeds and changes nothing

#### Scenario: Baseline has no business tables

- GIVEN a database with only the baseline applied
- WHEN its tables are listed
- THEN only migration-tracking structures exist

### Requirement: Migration execution path

Migrations MUST run from Node using a direct (non-pooled) connection string and MUST NOT run inside the Worker. The migration script MUST validate its configuration with the shared environment schema before connecting. (Source: proposal 4.5, 4.6)

#### Scenario: Missing connection string

- GIVEN no migration connection string is configured
- WHEN the migration script starts
- THEN it exits non-zero naming the missing variable and prints no values

### Requirement: Local and CI test database

`pnpm test` MUST obtain a real PostgreSQL 17 instance without Docker: by default via the `embedded-postgres` package (PostgreSQL 17.x binaries for win-x64 and linux-x64), started by Vitest global setup on a random free port and stopped at the end. If `TEST_DATABASE_URL` is set, tests MUST use that external instance instead and MUST NOT start an embedded one. The same default path MUST be used locally and in CI. (Source: OD-1; proposal 4.4)

#### Scenario: Fresh clone, no setup

- GIVEN a fresh clone on Windows or Linux with Docker not running and `TEST_DATABASE_URL` unset
- WHEN `pnpm i && pnpm test` runs
- THEN an embedded PostgreSQL 17 starts, DB-backed tests pass and the process is stopped afterwards

#### Scenario: External override

- GIVEN `TEST_DATABASE_URL` pointing at a reachable PostgreSQL
- WHEN `pnpm test` runs
- THEN no embedded instance is started and tests run against the external URL

#### Scenario: Port conflict avoided

- GIVEN another PostgreSQL already listens on port 5432
- WHEN the embedded instance starts
- THEN it uses a different free port and tests pass

#### Scenario: Binaries unavailable for the platform

- GIVEN a platform without embedded binaries and no `TEST_DATABASE_URL`
- WHEN `pnpm test` runs
- THEN the DB-backed suite fails with a message instructing to set `TEST_DATABASE_URL` (no silent skip)

### Requirement: Test database lifecycle helper

A helper in `src/testing` MUST provide each DB-backed test file or suite with an isolated database (or schema) migrated from scratch, and MUST clean it up afterwards, so later integration and concurrency tests are not order-dependent. Tests MUST NOT connect to Neon. (Source: proposal Scope #9, Risks)

#### Scenario: Isolation between suites

- GIVEN two suites that each insert a row into the same table
- WHEN they run in parallel
- THEN neither observes the other's rows

#### Scenario: Cleanup

- GIVEN a finished suite
- WHEN its teardown completes
- THEN its isolated database or schema no longer exists

### Requirement: Runtime connection through Hyperdrive

In the Worker, the database client MUST be created from the Hyperdrive binding using one driver (`node-postgres`) shared with Node scripts and tests. Local development MUST use a local connection string instead of Hyperdrive. (Source: proposal 4.5, Scope #10)

#### Scenario: Deployed path

- GIVEN a deployed Worker with a Hyperdrive binding to the Neon `staging` branch
- WHEN `/status` is requested
- THEN the probe query succeeds through Hyperdrive

#### Scenario: Local development

- GIVEN a local connection string in `.dev.vars`
- WHEN the dev server handles `/status`
- THEN the probe uses that connection string

### Requirement: Neon layout

The Neon setup MUST be one project in `aws-sa-east-1` on PostgreSQL 17 with branches `main` (production, untouched until launch) and `staging` (used by the workers.dev deployment). Provisioning requires explicit owner authorization and credentials (OD-2, pending); this spec does not prescribe how they are provisioned. (Source: OD-4)

#### Scenario: Branch roles

- GIVEN the Neon project
- WHEN branches are listed
- THEN `main` and `staging` exist and only `staging` receives migrations during this change

#### Scenario: Provisioning without authorization

- GIVEN no owner authorization for Neon operations
- WHEN apply reaches a cloud step
- THEN the step is not executed and is reported as pending
