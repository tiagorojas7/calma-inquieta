## Decisions (technical)

- **Name key, not `lower(name)`** (owner, 2026-10-15; same as B3): PostgreSQL `lower()` under a C locale does not fold accented capitals ("LUCÍA" vs "Lucía" do not collide). The domain exports a pure `supplierNameKey(name)` = `trim()` + `normalize("NFC")` + `toLocaleLowerCase("es")`, exactly like `teacherNameKey`. Accents still differ: "Lucia" and "Lucía" are two names.
- **Schema (phase 2 only)**: `name_key text NOT NULL` with a partial unique index `UNIQUE INDEX ... ON (name_key) WHERE active`, mirroring `src/platform/db/schema/teachers.ts`. The Drizzle repository writes `name_key` on insert and update. Never edit an applied migration; regenerate the unmerged one after rebasing (design: numbering follows merge order).
- **Duplicate active name** is expressed with the kernel's existing `IssueCode "duplicate"` on `{ field: "name" }` inside `Invalid<SupplierField>` — the same representation B3 uses. The application port exposes a typed `SupplierNameConflictError`: both repository implementations map their unique-name backstop to it, and the service catches it and returns the typed duplicate-name result. The Drizzle adapter maps PostgreSQL SQLSTATE `23505` to this error; tests cover the race path where the pre-check passes but the write hits the unique index.
- **Ordering parity** (B3 review lesson): persistence order is normalized `name_key ASC`, then `id ASC`. The fake uses deterministic key comparison rather than locale collation. The shared contract includes non-ASCII `Álvaro` and `Ñandú` and expects the same order from fake and PostgreSQL.
- **NFC is proven** (B3 review lesson): the domain test compares a decomposed `Ñandu` with composed `Ñandu`, in addition to the accented-uppercase and accent-distinct cases.
- **`reactivate` gains `Invalid<"name">`**: the design lifecycle table says "Teacher, supplier, material: active↔inactive: Reactivation re-checks name uniqueness", but the B0b-b supplier contract omitted it. `application/contracts.ts` changes `reactivate` to `Promise<Result<Supplier, AdminFailure | NotFound | Invalid<"name">>>`, aligned with the teachers contract; `contracts.test.ts` is updated only where it pins the reactivate error union (verify in RED; do not weaken any other assertion).
- **Types move to the domain**: `SupplierDraft` and `SupplierField` move to `domain/supplier-core.ts` and are re-exported from `application/contracts.ts` (the B3 pattern: `teacher-core.ts` owns the draft/field types, `application/teachers.ts` re-exports them). Public imports from `~/modules/materials` are unchanged.
- **Validation limits** (design): name required, ≤120; phone optional, ≤30 and at least one digit; email optional, RFC-lite regex (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`, same as teacher-core); notes optional, ≤1000. Issue codes: `required`, `too-long`, `invalid-format`, `duplicate`.
- **Service shape mirrors B3**: `createSuppliersService(deps: SupplierServiceDeps): SupplierUseCases` with `deps { repository, clock, newId? }`, `requireAdminActor` first on every use case, duplicate check via `repository.findActiveByName` before insert/update, idempotent archive/reactivate, `list` filter ordered by name key then id. The port is the minimal slice shape — `insert`, `update`, `findById`, `findActiveByName`, `list` — deliberately without `findByIds`/`SupplierLookup`: no B8a consumer needs it, and B8b adds what its materials use cases require. The `SuppliersService.list` filter parameter keeps the B0b-b shape (optional `{ active?: boolean }`) — do not change published contracts beyond the reactivate error union.
- **Archived readable, not selectable**: `list({ active: true })` (the supplier select) excludes archived suppliers; `get`, `list` without filter and `findByIds` keep returning them. "Selectable" for B8b materials means the form only offers `active: true` suppliers.
